# notebooks

Colab notebooks for training and inference. Google Drive paths are set in the first cell of each notebook.

| Notebook | What it does | Needs a GPU |
|---|---|---|
| `semana1_higiene.ipynb` | Checks the model hashes against the pinned Hugging Face commit, recomputes the source reference with the conformal threshold calibrated on the validation split and evaluated on the test split, checks 16 vs 32 bit precision, and compares Bolivia against the source test split with chip-level bootstrap confidence intervals for each difference. Reads saved scores only; it does not run the model. | No |
| `semana2_t2_worldfloods.ipynb` | Downloads the WorldFloods v2 test split at a pinned Hugging Face revision, checks every file hash against Hugging Face, copies it to Google Drive, inspects bands, scale, grids and label encoding, and checks the band order from the native resolution of each band, since the files carry no band names (part A). Then computes, per map, the share of labeled pixels inside Sen1Floods11 countries and the cloud fraction, and applies the criteria in `prereg/t2_criterios.md` to write `t2_eventos.csv` (part B). It does not run the model. | No |
| `semana2_t2_janelas.ipynb` | Cuts the T2 maps of the full set into 512 × 512 windows following `prereg/t2_janelas.md`, writes the windows that enter as 6-band images and labels, and writes `t2_janelas.csv`. Checks that every labeled cloud-free pixel is scored exactly once. It does not run the model. | No |
| `semana2_t2_janelas_nuvem050.ipynb` | Applies the same window rule, unchanged, to the three maps added by the cloud 0.50 sensitivity (EMSR286 two maps, EMSR347 Zomba on 2019-03-12), appends their windows to the same window folder and writes `t2_janelas_nuvem050.csv`, leaving `t2_janelas.csv` as it was. Checks that every labeled cloud-free pixel is scored exactly once. It does not run the model. | No |
| `semana3_regimes.ipynb` | Installs TerraTorch 1.2.11 with `peft` pinned, records the pretrained backbone `Prithvi_EO_V2_300M_TL.pt` by Hugging Face revision and SHA-256 and copies it to Google Drive, then builds the three fine-tuning regimes (frozen encoder, LoRA, full fine-tuning) with that backbone loaded. Checks the trainable parameter counts against the pre-registration draft, that the encoder tensors equal the pinned file, and a forward pass. It trains nothing and reads no imagery. If Google Drive cannot be mounted it continues on local disk. | Yes, for the forward pass only |
| `semana4_piloto_sementes.ipynb` | Pilot of `prereg/piloto_sementes.md`: trains the frozen-encoder regime with seeds 101 and 102 (pilot-only seeds) at the learning rate chosen by the grid, runs 32-bit inference on the 89 validation chips and saves the logit margins, then compares both runs with the validation scores of the released checkpoint saved on 2026-06-07. Reports error rate, mIoU, error-detection AUROC, the conformal threshold and the unflagged error rate per model, the chip-bootstrap correlation between models, the per-chip correlation and the spread between seeds. Reads only the validation set. | Yes |
| `semana5_treino_confirmatorio.ipynb` | Confirmatory training runs of `prereg/preregistro.md` (section 4): the frozen-encoder regime (R1, learning rate 5e-4), full fine-tuning (R3, 5e-5) and LoRA (R2, r = 16, 5e-4, secondary) with seeds 1 to 5 (runs already finished on Google Drive are skipped), 50 fixed epochs, validation mIoU logged every 5 epochs. Applies the failure rule (non-finite loss or validation mIoU below 0.80 at epoch 50: repeat once, then seed 6 replaces the seed), runs 32-bit inference on the 89 validation chips and saves the logit margins and the trained weights. Reads only the validation set. | Yes |
| `semana6_inferencia_alvos.ipynb` | Runs the 15 confirmatory models (R1, R2, R3, seeds 1 to 5) in 32 bits on whole 512 × 512 chips and windows of the validation set, the source test, Bolivia and the T2 windows (441 of the full-set sensitivity plus 120 of the cloud 0.50 maps), and saves the logit margin of every scored pixel under three randomly drawn regime codes; the code key goes to a separate folder and is never shown. Rebuilds the label files with the boundary flag, checks the validation margins against the ones saved at training, and has an optional test-time augmentation cell (8 dihedral transforms). Rio Grande do Sul is not included. | Yes |
| `semana7_analise_final.ipynb` | The single run of the frozen analysis script on the margins of the 15 runs: checks the script files against the SHA-256 table in `analysis/README.md`, copies the margins to local disk and checks them against `manifesto_sha256.csv`, checks the inputs against `splits/` without computing any metric, runs `analysis/analise_congelada.py` (about 4 hours, no test-time augmentation) and copies the tables and the log to Google Drive. The script reads the regime key only after processing all runs. | No |
| `semana8_exploratorias.ipynb` | Exploratory analyses E1, E2, E4 and E6 of `prereg/plano_exploratorio.md` (`analysis/exploratoria/exploratorias.py`): checks the frozen scripts and the margins, checks that tau, AUROC_e per event, the unflagged error rate and the pooled ensemble values match the confirmatory run, and writes tables and figures to a folder of their own (`resultados/semana8/exploratorias`). | No |
| `semana8_e3_borda.ipynb` | Exploratory analysis E3 of `prereg/plano_exploratorio.md` (`analysis/exploratoria/e3_borda.py`): downloads the Sen1Floods11 labels and checks them against the week-6 hashes, re-reads the T2 scene and window labels from Google Drive, computes the distance of every scored pixel to the label boundary (checked against the labels and boundary flags of the inference), then the metrics per distance band and the per-unit correlations of RQ3, written to `resultados/semana8/e3`. | No |
| `semana8_e5_r0.ipynb` | Exploratory analysis E5 of `prereg/plano_exploratorio.md`: runs the released checkpoint (R0, commit `918b9f1`, weights and `config.yaml` checked by SHA-256) with the reading, preprocessing and 32-bit inference code of `semana6_inferencia_alvos.ipynb` on the validation set, the source test and Bolivia, after checking the labels against the week-6 label files and comparing the recipe of the `config.yaml` with the week-6 model; then `analysis/exploratoria/e5_r0.py` writes the metrics next to the week-1 values to `resultados/semana8/e5`. | Yes |
| `semana9_rq4_exportacao.ipynb` | Step 1 of `prereg/plano_rq4.md`: asks Google Earth Engine for the Sentinel-2 L1C granules of tiles 22JDM, 22JCN and 22JDN (added on 2026-11-02) sensed on 2024-05-06 (`COPERNICUS/S2_HARMONIZED`, bands B2, B3, B4, B8A, B11, B12 at 10 m, plus the s2cloudless probability and the L2A scene classification of the same granule), takes the one with the lowest cloud cover, checks the offset, places each exported file on the full 10980 x 10980 grid of its granule by whole-pixel offsets (Earth Engine crops exports to the image footprint), checks the grid, and writes the product IDs and the SHA-256 of the raw and placed files to `rq4_entradas.json`; on a second run, files already exported are not exported or rewritten again and their SHA-256 must match the record in the repository. It runs no model and reads no reference. | No |
| `semana9_rq4_referencias.ipynb` | Step 2 of `prereg/plano_rq4.md`: downloads the candidate references (metadata of Copernicus EMS EMSR720, the EMSN194 package, the main GeoPackage of the UFRGS database on Zenodo, record 14617475, checked by its MD5) and writes an inventory of every layer (dates in the layer and file names, features, classes, area inside each tile) with `analysis/rq4/inventario_referencias.py`. Nothing is rasterized and no model is run. | No |
| `semana9_rq4_emsr720.ipynb` | Step 2b of `prereg/plano_rq4.md`: downloads the five Copernicus EMS EMSR720 grading products (GRA_PRODUCT, Pléiades Neo images of 2024-05-06, AOI 1 to 5), checks the zip files, extracts the vector layers (not the images) and writes an inventory of every layer with `analysis/rq4/inventario_referencias.py`, with the area inside each of the three tiles and the classes of the `observedEvent` layers; copies those layers to the output folder. Nothing is rasterized and no model is run. | No |
| `semana9_rq4_auxiliares.ipynb` | Step 1b of `prereg/plano_rq4.md`: asks Google Earth Engine for permanent water (JRC Global Surface Water 1.4, `occurrence`) and the ESA WorldCover 2021 map on the 10 m grid of each of the three tiles, places them on the whole 10980 x 10980 grid by whole-pixel offsets, builds them on the local disk, copies them to the Drive, remounts the Drive and checks the SHA-256 again, and writes `rq4_auxiliares.json`. A file already in the Drive is never rewritten: it is only checked against what the raw export gives. It runs no model and reads no reference. | No |
